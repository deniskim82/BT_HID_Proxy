# BT_HID_Proxy

![Build Status](https://github.com/deniskim82/BT_HID_Proxy/actions/workflows/build.yml/badge.svg)

ESP32와 CH9329를 이용한 BLE 키보드 → USB HID 변환기입니다.

*[English version](README.md)*

## 개요

블루투스를 지원하지 않는 PC에서 BLE 키보드를 사용할 수 있게 해줍니다. ESP32가 BLE HID(HOGP) 호스트가 되어 페어링된 키보드의 입력을 받고, CH9329(UART→USB HID 변환 칩)를 통해 PC에 일반 USB 키보드처럼 전달합니다. PC 입장에서는 그냥 USB 키보드가 꽂힌 것으로 보이므로 드라이버 설치나 별도 설정이 필요 없습니다.

```
[BLE 키보드] ---(BLE / HOGP)---> [ESP32 / NimBLE] ---(UART)---> [CH9329] ---(USB HID)---> [PC]
```

> **참고:** 이 펌웨어는 **BLE 전용**입니다(NimBLE 스택). 클래식 블루투스 키보드는 지원하지 않습니다.
> 최근 10년 내에 나온 키보드는 사실상 모두 BLE를 지원하며, BLE 쪽이 입력 지연이 더 낮고
> (연결 간격 7.5~15ms) 재연결도 훨씬 안정적입니다. 정확한 수치는
> [기술 사양](#기술-사양) 참고.

## 하드웨어

### 대상 보드
- **M5Stamp Pico** (ESP32-PICO-D4)
  - 작은 크기
  - 내장 버튼 (GPIO39)
  - RGB LED SK6812 (GPIO27) — 상태 표시등

### 필요한 부품
- M5Stamp Pico 또는 호환 ESP32 보드
- CH9329 UART→USB HID 모듈
- BLE 키보드

### 배선

**TX와 RX는 서로 교차해서 연결합니다.**

| M5Stamp Pico | CH9329 모듈 |
|--------------|-------------|
| GPIO32 (TX)  | **RXD**     |
| GPIO33 (RX)  | **TXD**     |
| GND          | GND         |
| 3.3V         | VCC (USB로 전원을 공급받는다면 연결하지 않아도 됨) |

**참고**
- CH9329 모듈은 보통 PC의 USB에서 전원을 공급받습니다.
- UART는 **115200 baud, 8비트, 패리티 없음, 스톱비트 1개, 흐름제어 없음**으로 동작합니다.
- CH9329의 공장 기본 속도는 9600입니다. 설정되지 않은 모듈이라면 펌웨어가 자동으로 감지해 9600으로 통신하지만, 지연이 커지므로 제조사 설정 도구로 115200으로 바꾸는 것을 권장합니다.
- **RXD 선(GPIO33)은 키 입력 자체에는 필요하지 않습니다.** 다만 이 선이 있어야 Caps/Num/Scroll Lock 상태를 PC에서 키보드로 전달할 수 있고, 문제 발생 시 진단도 가능합니다.

## 기능

- **NimBLE 기반 BLE HOGP 호스트** — 가볍고 재연결이 빠르고 안정적입니다
- **HID 리포트 맵 해석** — 키보드가 실제로 어떤 리포트로 키를 보내는지 디스크립터를 읽어 판별합니다. 확인된 키보드 리포트만 전달하므로, 미디어/벤더/배터리 리포트가 키 입력으로 잘못 해석되는 일이 없습니다 (예전 펌웨어에서 *재연결 후 임의의 키가 무한 입력되던* 문제의 근본 원인이었습니다)
- **소스 키보드는 6KRO/NKRO 모두 지원** — 어느 모드로 동작하든 차이 없이 동작합니다. 두 방식 모두 눌린 키 목록으로 정규화한 뒤 6키 제한을 적용하기 때문입니다. 다만 **PC로 나가는 리포트는 CH9329 프로토콜 제약으로 동시 6키(6KRO)까지만** 전달됩니다 — 자세한 내용은 [기술 사양](#기술-사양) 참고
- **미디어 키 및 시스템 키 지원** — 볼륨 조절, 음소거, 재생/일시정지, 이전/다음 곡, 브라우저 및 애플리케이션 단축키, 전원/절전/깨우기
- **부트 프로토콜 폴백** — 리포트 맵이 특이한 키보드에 대비
- **자동 재연결** — 키보드의 광고 신호 탐색과 직접 연결 시도를 번갈아 수행합니다
- **페어링 유지** — 전원을 껐다 켜도 페어링이 유지됩니다 (NimBLE 본드 저장소 + NVS)
- **재페어링 자동 복구** — 키보드가 다른 기기에서 페어링 슬롯을 덮어써 본드가 깨진 경우, 이를 감지해 자동으로 다시 페어링합니다
- **LED 상태 동기화** — PC의 Caps/Num/Scroll Lock 상태를 키보드로 전달합니다
- **키 눌림 방지** — BLE 연결이 끊어지면 PC 쪽 키를 모두 떼어 놓아, 키가 눌린 채 남는 일이 없습니다
- **UART 단일 송신자 구조** — 모든 CH9329 프레임이 하나의 송신 태스크를 거치므로 프레임이 서로 섞이지 않습니다 (예전에 키 입력이 가끔 누락되던 원인)
- **페어링 모드** — 버튼을 5초간 길게 누르면 새 키보드를 페어링합니다
- **패스키 없는 페어링** — 연결은 LE Secure Connections로 암호화되지만, 코드를
  입력하거나 확인할 일은 없습니다 ([보안 모델](#보안-모델) 참고)

## 사용 방법

### 평소 사용
1. 전원이 들어오면 NVS에 저장된 키보드를 불러옵니다
2. 해당 키보드의 광고 신호를 탐색합니다 (주기적으로 직접 연결도 시도)
3. 연결 → 암호화 → HID 서비스 탐색 → 키보드 리포트 구독 후 입력 전달을 시작합니다
4. 연결이 끊어지면 자동으로 재연결합니다

### 새 키보드 페어링
1. 키보드를 페어링 모드로 전환합니다
2. M5Stamp Pico의 버튼을 **5초 이상** 길게 누릅니다
3. 약 6초간 탐색한 뒤 신호가 가장 강한 키보드에 연결합니다
4. 패스키 입력 과정은 없습니다. 그대로 페어링이 완료됩니다
5. 새 페어링이 기존 페어링을 대체합니다

> 최초 페어링은 믿을 수 있는 장소에서 하세요. 이유는 [보안 모델](#보안-모델)에
> 설명되어 있습니다.

### 상태 표시등

색은 의미를, 점멸 속도는 긴급도를 나타냅니다. 빨간색은 오류일 때만 사용합니다.

| 상태 | 설명 | LED 패턴 |
|------|------|----------|
| 대기 | 저장된 페어링 없음 | 주황색 느린 점멸 (1초) |
| 탐색 중 | 페어링된 키보드를 찾는 중 | 파란색 느린 점멸 (1초) |
| 페어링 | 페어링 모드 | 파란색 빠른 점멸 (200ms) |
| 연결 중 | 연결을 맺는 중 | 파란색 상시 점등 |
| 연결됨 | 정상 동작 중 | 초록색 은은한 상시 점등 |
| 오류 | 연결 오류 (자동 재시도) | 빨간색 빠른 점멸 (200ms) |

## 펌웨어 설치

### 방법 1: 미리 빌드된 펌웨어 사용 (권장)

GitHub Actions가 커밋마다 펌웨어를 자동으로 빌드합니다.

1. [Actions](https://github.com/deniskim82/BT_HID_Proxy/actions) 탭으로 이동
2. 가장 최근의 성공한 빌드를 선택
3. 아티팩트(`.bin` 파일과 플래시 스크립트 포함)를 내려받아 압축 해제
4. 플래시 실행:
   ```bash
   chmod +x flash.sh
   ./flash.sh /dev/ttyUSB0
   ```

### 방법 2: 직접 빌드

**준비물:** [ESP-IDF v5.1 이상](https://docs.espressif.com/projects/esp-idf/en/v5.1.2/esp32/get-started/)

```bash
idf.py set-target esp32
idf.py build
idf.py -p <포트> flash
idf.py -p <포트> monitor
```

> `sdkconfig.defaults`가 변경된 커밋을 받은 경우에는 `sdkconfig` 파일을 지우고 다시 빌드해야 반영됩니다. 소스 코드만 바뀌었다면 그냥 `idf.py build`로 충분합니다.

## 기술적인 내용

### 데이터 흐름

```
NimBLE 호스트 태스크        CH9329 송신 태스크         CH9329 수신 태스크
-------------------        ------------------        ------------------
알림(notification) 수신
  → 리포트 맵 기반으로
     8바이트 부트 리포트로
     변환
  → 큐에 넣기  ---------->  중복 제거 + 프레임 구성
                           → uart_write_bytes
                                                     LED 상태 프레임 수신
                                                     → BLE로 키보드에 전달
```

입력 경로에는 지연을 유발하는 블로킹 호출이 전혀 없습니다.

### CH9329 프로토콜

```
[0x57][0xAB][주소][명령][길이][데이터...][체크섬]
```

| 명령 | 의미 |
|------|------|
| 0x01 | GET_INFO (칩 버전, USB 연결 상태, LED 상태) |
| 0x02 | 키보드 리포트 전송 |
| 0x03 | 미디어 / 시스템 키 전송 |
| 0x08 | 저장된 설정 읽기 |
| 0x0D | **RESET** (LED 조회 명령이 아닙니다 — 아래 참고) |

체크섬은 앞선 모든 바이트의 합(mod 256)입니다.

> **주의:** `0x0D`는 리셋 명령입니다. 예전 펌웨어는 이를 "LED 상태 조회"로 잘못 알고
> 연결할 때마다, 그리고 Lock 키를 누를 때마다 전송했습니다. 그 결과 CH9329가 리셋되면서
> USB 연결이 끊어져 Windows에서 *"알 수 없는 USB 장치(장치 설명자 요청 실패)"*가
> 발생했습니다. LED 상태는 `GET_INFO`(0x01) 응답에 포함되어 있습니다.

### 미디어 키 변환

CH9329는 HID usage 코드가 아니라 **고정된 비트맵**을 사용합니다. 그래서 키보드가 보낸 consumer usage를 CH9329의 비트 위치로 변환합니다.

| 키보드가 보내는 usage | CH9329 기능 |
|---|---|
| 0x00E9 / 0x00EA | 볼륨 증가 / 감소 |
| 0x00E2 | 음소거 |
| 0x00CD | 재생 / 일시정지 |
| 0x00B5 / 0x00B6 | 다음 곡 / 이전 곡 |
| 0x00B7 / 0x00B8 | 정지 / 꺼내기 |
| 0x0221~0x0227 | 브라우저 (검색, 홈, 뒤로, 앞으로, 정지, 새로고침) |
| 0x0192 / 0x0194 / 0x019E | 계산기 / 내 컴퓨터 / 화면 잠금 |
| 0x0081~0x0083 | 전원 / 절전 / 깨우기 |

CH9329에 대응하는 기능이 없는 usage(예: 화면 밝기 조절)는 보내지 않고 무시합니다.

### 예전 문제들이 해결된 이유

| 증상 | 원인 | 해결 |
|---|---|---|
| 다른 기기에 연결했다가 돌아오면 임의의 키가 무한 입력됨 | 8바이트짜리 리포트면 무조건 키 입력으로 간주해 전달. 가짜 키 눌림에 대응하는 뗌 신호가 오지 않음 | 리포트 맵을 해석해 검증된 키보드 리포트만 구독·전달 |
| 가끔 키 입력이 누락됨 | 여러 태스크가 동시에 UART에 써서 프레임이 섞이고, CH9329가 손상된 프레임을 버림 | 단일 송신 태스크 + 큐로 직렬화 |
| Caps/Num/Scroll 이후 입력이 밀림 | 입력 콜백 안에서 50ms 대기 | LED 조회를 별도 타이머로 분리, 입력 경로는 절대 대기하지 않음 |
| 간헐적 먹통 / 재부팅 | 정렬되지 않은 `uint64_t` 읽기로 Xtensa 정렬 예외 발생 | `memcmp`로 교체 |
| USB 인식 실패 (장치 설명자 요청 실패) | `0x0D`(리셋)를 LED 조회로 오인해 전송 | `GET_INFO`(0x01)로 변경 |
| 키보드 LED 상태가 한 번도 동기화되지 않음 | 위와 동일 — 리셋 응답을 LED 상태로 해석 | `GET_INFO` 응답에서 LED 상태 추출 |
| 여러 키를 동시에 누르고 있으면 그 조합 전체가 계속 반복 입력됨(예: `asdfg`가 반복) | 6KRO 리포트와 NKRO 리포트를 모두 구독하는 키보드에서, 둘을 같은 병합 상태 슬롯에 저장. 순간적으로 비어있는 쪽 리포트가 활성 쪽의 키를 계속 지움 | 구독한 리포트마다 독립된 상태 슬롯 부여 (`key_state.c`) |

## 기술 사양

| 항목 | 값 |
|---|---|
| BLE 프로토콜 버전 | **Bluetooth 4.2** — 원판 ESP32의 무선칩이 구현하는 스펙은 BLE 4.2입니다. Bluetooth SIG의 BLE 5.0 **인증**은 하위 호환 목적으로 받았지만, 5.0 전용 신규 기능(2M PHY, Extended Advertising, LE Coded PHY/Long Range 등)은 구현하지 않습니다 |
| 연결 간격 | 7.5~15ms (요청 범위, `ble_hid_host.c`) — 실제 값은 키보드와 협상해 그 범위 내에서 결정됩니다 |
| 입력 레이트 상한 | 약 67~133Hz — 전적으로 BLE 연결 간격이 결정하며, UART 링크와는 무관합니다 (아래 지연시간 표 참고) |
| PC로 전달되는 키 수 | **동시 6키(6KRO)** — CH9329 키보드 명령(0x02)이 8바이트 부트 리포트를 받는 데서 오는 하드 리밋입니다. 모디파이어(Ctrl/Shift/Alt/GUI)는 별도 바이트라 이 제한과 무관합니다 |
| 소스 키보드 롤오버 | 6KRO 또는 NKRO, 둘 다 동일하게 동작 (위 NKRO 지원 항목 참고) |
| UART 링크 (ESP32 ↔ CH9329) | 115200 baud, 8비트 데이터, 패리티 없음, 스톱비트 1개, 흐름제어 없음 |
| UART 대역폭 사용률 | 입력 레이트 상한에서도 약 16% (14바이트 프레임 1회 ≈ 1.2ms, 약 11.5kB/s 링크 기준) |
| 페어링 보안 | LE Secure Connections(LESC/ECDH), 패스키 없는 Just Works 방식 ([보안 모델](#보안-모델) 참고) |
| 동시 연결 키보드 수 | 1대 (확장 시 필요한 작업은 `CLAUDE.md` 참고) |

### 예상 입력 지연시간

프로토콜 타이밍을 근거로 한 추정치이며, 실측값이 아닙니다.

| 구간 | 지연시간 | 비고 |
|---|---|---|
| BLE 무선 구간 | 7.5~15ms | 연결 간격 1회, 키보드 → ESP32 |
| ESP32 처리 (파싱·합성·큐잉) | 0.1ms 미만 | 이 경로에는 어떤 지연도 넣지 않음 |
| UART 프레임 전송 (14바이트 @ 115200) | 약 1.2ms | 헤더(5) + 데이터(8) + 체크섬(1) |
| CH9329 내부 처리 → USB | 수 ms | 데이터시트에 명시되지 않음. Full-Speed HID 인터럽트 엔드포인트 통상 수준 |
| **합계 (대략)** | **약 10~20ms** | 일반적인 RF 동글 무선 키보드와 비슷한 수준이며, 사람이 체감하는 지연 기준(약 200ms)에 한참 못 미침 |

## 보안 모델

**보호되는 것.** 모든 BLE 연결은 LE Secure Connections(ECDH 키 교환, AES-CCM)로
암호화됩니다. 무선 신호를 도청하더라도 키 입력 내용을 복원할 수 없습니다.
타이핑 중에도, 페어링 과정을 통째로 캡처한 뒤 나중에 복호화하려 해도 마찬가지입니다.
최초 페어링 이후에는 본딩 키(LTK)가 NVS에 저장되어 재사용되므로, 페어링 절차
자체가 다시 일어나지 않습니다.

**보호되지 않는 것.** 페어링은 *Just Works* 방식이라 상대 장치를 인증하지
않습니다. 최초 페어링이 이루어지는 몇 초 동안, 물리적으로 가까운 곳에서 BLE
장비를 갖춘 공격자가 키보드와 프록시 사이에 끼어드는 것이 원리적으로 가능합니다.

**왜 이렇게 만들었는가.** 그 공격을 막으려면 Passkey Entry나 Numeric Comparison
같은 인증 방식이 필요하고, 두 방식 모두 공격자가 개입할 수 없는 경로로 무작위
6자리 숫자를 주고받아야 합니다. 이 보드에는 RGB LED가 하나뿐입니다. 6자리 숫자를
표시할 수도, 입력받을 수도 없습니다. 예전 펌웨어는 패스키를 `123456`으로
고정해 두는 방식으로 이 문제를 덮었지만, 그 값은 이 README에까지 적혀 있었으니
비밀이 아니었고 결국 아무것도 보호하지 못하면서 사용자에게 6자리 입력만 요구한
셈이었습니다. 이제는 장치가 자신의 실제 능력(`NO_IO`)을 그대로 선언합니다.
블루투스 표준상 한쪽이라도 `NO_IO`면 Just Works로 결정되며, 키보드가 그래도
패스키를 요구하면 인증하는 척하는 대신 페어링을 거부합니다.

**실제로 지켜야 할 것.** 최초 페어링은 믿을 수 있는 장소에서 하세요. 집이나
사무실 책상에서 하시고, 카페·공항·행사장 같은 곳은 피하시는 것이 좋습니다.
단 몇 초짜리 1회성 구간이며, 그 이후로는 저장된 본딩 키로 연결되므로 페어링이
다시 일어나지 않습니다. 새 키보드로 바꾸거나 본딩이 지워져 다시 페어링하게 될
때도 같은 원칙을 지키시면 됩니다.

## 문제 해결

### 키보드가 연결되지 않음
1. 키보드가 페어링 모드인지 확인
2. 프록시 버튼을 5초 이상 길게 눌러 페어링 모드 진입
3. 시리얼 모니터(115200)에서 탐색 결과 확인 — 광고에 HID 서비스 UUID나 appearance가 있는 키보드만 인식합니다

### 키보드가 코드를 요구함 / 페어링 중 LED가 빨갛게 됨
이 장치는 입력·표시 수단이 없다고 선언하므로, 정상적인 경우 코드 입력 없이
페어링이 끝납니다. 그럼에도 키보드가 패스키를 고집하면 프록시는 연결을 거부하고
중단합니다. LED가 약 5초간 오류 패턴을 표시하고, 로그에
`Keyboard demands authenticated pairing` 이 남습니다. 이 하드웨어에서는 우회할
방법이 없습니다([보안 모델](#보안-모델) 참고). 키보드에 따라 패스키를 요구하지
않는 연결 모드(보통 "PC/태블릿" 프로파일)가 있으니 그쪽을 시도해 보시고, 없다면
이 프록시로는 사용할 수 없습니다.

### 키 입력이 PC에 전달되지 않음
시리얼 모니터에 부팅 직후 나오는 진단 로그를 확인하세요.

| 로그 | 의미 |
|---|---|
| `UART self-test PASSED` | ESP32 내부 UART 경로 정상 |
| `TX KB: ... (drain=ESP_OK)` | 바이트가 실제로 TX 핀 밖으로 나감 |
| `RX frame: CMD=0x82 (keyboard ACK)` | CH9329가 프레임을 정상 수신 중 |
| `CH9329 INFO: ... usb_status=0x01` | CH9329가 PC에 정상 인식됨 |
| `did not answer at any baud rate` | CH9329 무응답 — 전원, RXD 배선, 또는 칩 상태 확인 |

### Windows에서 "알 수 없는 USB 장치"로 표시됨
드라이버 문제가 아닙니다. CH9329는 표준 HID 장치라 드라이버가 필요 없으며, 이 오류는 드라이버가 개입하기 전 단계에서 발생합니다. 확인 순서:

1. USB 케이블 교체 (충전 전용 케이블은 데이터선이 없습니다)
2. CH9329 모듈만 PC에 연결해 인식되는지 확인
3. D+/D− 배선 및 납땜 상태 확인

### 빌드 오류
1. ESP-IDF v5.1 이상인지 확인
2. `idf.py set-target esp32` 실행 후 빌드
3. 그래도 안 되면 `idf.py fullclean && idf.py build`
